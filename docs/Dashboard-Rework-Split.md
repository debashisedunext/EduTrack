# Dashboard Rework — Two-Person Split (shared rules)

Companion to [`Dashboard-Rework-Plan.md`](Dashboard-Rework-Plan.md), which stays the authority on **what** is built. This document is the authority on **who owns which file**. The per-person backlogs are [`Dashboard-Rework-Dev1.md`](Dashboard-Rework-Dev1.md) and [`Dashboard-Rework-Dev2.md`](Dashboard-Rework-Dev2.md). Read this file once, then work from your own.

## The cut: vertical, not layered

**Dev 1 takes the foundations and the Today tab. Dev 2 takes Overview, Weekly and `module-open` — full stack, migration to pixel.**

A layered cut (one person backend, one frontend) was the obvious split and is wrong here for two reasons: it serialises Dev 2 behind every endpoint, and it puts all of the genuinely difficult work — working-calendar maths, per-cycle stamps, backfill honesty — on one person. Dev 2 has the deeper half by design: the whole API contract, three verticals against Dev 1's one, the nested `groupTickets` roll-up, ISO-week maths, two keyboard-accessible Recharts widgets, and a new summary table of their own.

| | **Dev 1 — Foundations + Today** | **Dev 2 — Overview + Weekly + Modules** |
|---|---|---|
| PRs | 1, 2, 3, 4, 5, 6, 7, 8 | H1, 9, 10, 11, 12, 13, 14 |
| Contract | consumes it — never edits it | **owns `contracts/openapi.yaml` outright**, both halves, plus every regeneration of the client |
| Backend | `ticket_cycles` stamps · `daily_ticket_stats` + `resource_daily_stats` counters · `TodayStatsRepository` · `nextWorkingDay` · `TodayProgressService` | `OverviewService` · weekly counters + `WeeklyStatsRepository` · `WeeklyProgressService` · `module_daily_stats` + `ModuleStatsRepository` · the `module-open` `WidgetService` branch |
| Frontend | `ui/tabs.tsx` · the tab shell · Analytics verbatim move · Today cards, MIS table, sections | Overview cards + `TopAssigneesBar` + `StatusDistributionDonut` · `WeekPicker` + `weeklyRange` · `GroupedTicketAccordion` + `groupTickets` · `ModuleOpenBar` |
| Stream C sign-off | `TicketListController` params · `ticket_cycles` stamping at transition · `TicketDetailTabs` wrapper | none |

Dev 1 crosses every stream boundary. Dev 2 crosses none — one `/notify-stream` message to Divyansh on day one covers the whole feature.

## Why this is conflict-free

The four files a vertical split would normally collide in are each neutralised deliberately:

1. **`contracts/openapi.yaml`** — **Dev 2 owns it outright.** They author the entire delta on day one (H1) — Dev 1's `/dashboard/today` and `GET /tickets` blocks as well as their own three — commit it, and regenerate the client. Dev 1 never opens the file. This is stricter than splitting it by path block, and strictly better: a file with one author cannot conflict at all, and the diff-by-region rule that would otherwise govern it is the kind of rule that holds until the first hurried afternoon.
2. **`DashboardController.java`** — Dev 1 lands all three routes as stubs in PR 2, before either service exists. After that each person only fills in their own service class; nobody edits the controller again.
3. **The worker recompute** — new counters go in **new per-concern repository classes** (`TodayStatsRepository`, `WeeklyStatsRepository`, `ModuleStatsRepository`), not appended to `DailyStatsRepository`. This follows CLAUDE.md's feature-packaging rule and removes the single worst contention point in the feature. `StatsRefreshWorker` gains one call line per class — Dev 1 adds all three call sites in PR 4, wired to classes that start empty.
4. **The frontend shell** — `DashboardPage.tsx` and `useDashboardFilters.ts` are Dev 1's in PR 2 and frozen after it. Dev 2 mounts into `tabs/overview/` and `tabs/weekly/` and never edits the shell.

Migrations need no rule: timestamp versioning means two people adding columns on the same day produce two different files.

**Small append-only lists** — `DrillDownContractTest.SOURCES`, `RouteInventory`, `WIDGET_CATALOG` — take one appended line each from both people. Append at the end, never reorder. A one-line append conflict is a ten-second resolve; a reordered list is an afternoon.

**`frontend/src/api/generated/`** — regenerated by Dev 2 only, since Dev 2 owns the contract that produces it. Dev 1 rebases to pick it up and never runs `npm run api:generate`. If a conflict somehow appears there, do **not** merge by hand: take either side and re-run the generator. It is generated output; the generator is the resolution.

## Cross-person dependencies

The bulk still runs one way — **Dev 2 waits on Dev 1 at four points** — but with the contract in Dev 2's hands, **Dev 1 now has a standing dependency of their own**, on day one and on every amendment after it.

| Dev 2 needs | from Dev 1 | for |
|---|---|---|
| the three `DashboardController` route stubs | PR 2 | PRs 9, 12 |
| the tab shell and `?tab=` | PR 2 | PRs 10, 13 |
| the new counters + their two worker call sites | PR 4 | PRs 9, 11 |
| `statusCategory` / `statuses` on `GET /tickets` | PR 5 | PR 13, and the drill-downs in PR 14 |

| Dev 1 needs | from Dev 2 | for |
|---|---|---|
| the frozen contract + generated client | H1 | PR 5 and PR 6 — their whole backend line |
| every later contract amendment | on request | anything the frozen shape got wrong |
| the class names of `WeeklyStatsRepository` and `ModuleStatsRepository` | H1 | wiring the two empty call sites into `StatsRefreshWorker` in PR 4 |

Three consequences worth planning around:

**H1 must finish on day one, and it is Dev 2's job to make sure it does.** The contract now gates Dev 1's PR 5 — and PR 5 is one of the two PRs *Dev 2* is waiting on. A slow contract loops back onto its own author: Dev 2 delays PR 5, PR 5 delays PR 14's Ready flip and PR 13. Nobody else can unpick that knot.

**Dev 1's PRs 2, 4 and 5 are still the project schedule.** PRs 6, 7 and 8 serve nobody but Dev 1's own tab. If Dev 1 falls behind, the things that slip are 6–8, never 2, 4 or 5.

**Dev 2 has several days of genuinely unblocked work** — `groupTickets.ts`, `weeklyRange.ts`, and all of PR 14 except its drill-down URLs. Start there, not by waiting.

## Rules both people follow

- Branch from `develop`, rebase daily, never merge `develop` into your branch.
- Every PR opens as a **draft**, under ~400 lines, marked Ready only when your own unit and smoke tests are green.
- **Neither of you merges anything.** Claude integrates in batches; a Ready PR is a request, not a licence.
- Task IDs go in commit **bodies** until the task is actually finished.
- No live `COUNT(*)` for any dashboard figure. Lists are live `GET /tickets` queries; figures come from summary tables, always.
- Every figure carries a `drillDown` URL built only from parameters `GET /tickets` implements, and every new URL-emitting service is registered in `DrillDownContractTest.SOURCES`.
- UTC everywhere in storage; working-calendar maths for anything due-shaped.
