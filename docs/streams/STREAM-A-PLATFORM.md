## M1 — Authentication & the scope guard · weeks 3–7

### Authentication
- [x] **A-020** Login endpoint — Argon2id (64 MB, 3 iterations), constant-time, **generic error messages** that never reveal which field failed. *(§10.1)*
  > `POST /api/v1/auth/login` in `api/feature/auth/`; hashing in `common/security/PasswordHashing` per TEAM-PLAN §6. Argon2id parameters are constants, not configuration — they are baked into every stored hash, so changing them is a re-hash migration rather than a config edit, and a tunable invites someone to lower it.
  > **Uniform timing.** An unknown username is verified against a decoy hash built once at startup, so every outcome costs one full KDF. Without it the endpoint answers "does this account exist?" in microseconds versus ~100 ms and becomes a staff directory. Asserted structurally (the encoder is invoked on both paths) rather than with a stopwatch, which would be flaky on a loaded runner and get muted.
  > **One failure mode.** Unknown user, wrong password and deactivated account all raise `InvalidCredentialsException`, which carries no field, and map to one `https://edutrack/errors/invalid-credentials` problem. `AuthLoginIT` asserts the bodies are byte-identical.
  > **No JPA entity.** B-005 (Ayush) owns the object model and has not started; auth reads a flat projection through `JdbcClient` instead of defining `User` first and making Stream A the de-facto owner of Stream B's mapping.
  > **Deliberately not included:** no token is issued (A-022) — the response omits `accessToken`/`expiresIn` rather than sending null, so A-022 is purely additive. No refresh cookie (A-023), no `failed_attempts`/lockout or per-IP rate limit (A-021), no forced-change redirect (A-026), no TOTP (A-029), no `last_login_at` or `LOGIN_SUCCESS` audit row (A-021/A-071). **Until A-021 lands there is no cap on guess volume — Argon2id's cost is the only brake.** S-01 (A-030) cannot complete a login against this endpoint yet.
  > **Two changes outside Stream A, both flagged for sign-off rather than made quietly:** springdoc 2.6.0 → 2.8.9 in `backend/pom.xml` (2.6.0 calls a `ControllerAdviceBean` constructor Spring 6.2 removed, so building the OpenAPI document throws `NoSuchMethodError` as soon as the app contains any `@ControllerAdvice` — latent for everyone, not just here), and the datasource exclusions dropped from `ContractConformanceTest` (Stream D) so the context can build a bean that reads the database. Both need Debashis.
- [x] **A-021** `failed_attempts` counter, 15-minute lockout at 5, email to Admin on lockout.
  > **The lock is reported only to someone who already knows the password.** The contract is explicit — lockout is "reported as `account-locked` only *after* correct credentials, for the same reason". So the password is verified first; a wrong password against a locked account still gets the generic 401. Checking the lock earlier would confirm the account exists to a stranger, and would answer faster than an unlocked one, leaking the same fact through timing.
  > **`locked_until` is an expiry, not a flag.** The lock lapses on its own with nothing scheduled to clear it. Applying a lock also zeroes the counter, so the window after it lifts is a fresh five rather than one mistake from re-locking.
  > **The writes live in `LoginAttemptRecorder`, a separate bean, with `REQUIRES_NEW`.** Recording a failure ends in a thrown exception and Spring rolls back on any unchecked throw — increment and throw in one transaction and the increment is undone, so no account would ever lock. The obvious fix (annotate a method on the same class) silently does nothing, because `@Transactional` is proxy-based and a self-call bypasses the proxy. Both failure modes leave every mocked unit test green, which is why `AuthLoginIT` proves the counter against a real database instead.
  > **Admin mail goes through Stream D's outbox** (`OutboxEnqueuer`), so it commits with the lock — an announced lockout that rolled back, or a lock with no announcement, are both worse than either alone. Two stated limits: D-035 throttles to one mail per recipient per minute and these carry no ticket id, so a burst of lockouts inside a minute reports the first only; and there is no ADMIN role to find until B-001 seeds it, so today this logs a warning and sends nothing. **The lock still applies — announcing it is best-effort, holding it is not.**
  > **Still open after this: the per-IP throttle, and the cost of a rejected attempt.** A per-IP limiter was built and then **deliberately removed** — keying on IP puts an entire office behind one NAT address into a single shared budget, so one colleague's typos can lock out everyone around them. Shipping that felt worse than the gap it closed. Two consequences to carry forward into **A-074**:
  > • A locked account still runs the full Argon2id verify before the lock is checked (~175 ms, 64 MB per attempt — measured), so the login endpoint remains the cheapest DoS target in the system. Short-circuiting on the lock is **not** the fix: it would make locked accounts answer faster than unlocked ones and leak which accounts exist.
  > • Nothing caps guess *volume*. The per-user counter stops repeated guessing at one account; it does nothing about one password sprayed across a thousand usernames, where no account ever reaches five failures.
  > A per-IP limit is the wrong shape for both. The design that actually fits is two-dimensional — cap attempts per `(IP, username)` **and** cap the number of *distinct* usernames tried per IP — so a clumsy colleague only ever affects their own account while a spray attack trips on its real signature. Recorded here rather than built, because it is A-074's scope and wants its own review.
  > **Fixed `RealtimeRelayIT` (Stream D) — flagged for Debashis.** D-012 merged before A-020 and excludes `DataSourceAutoConfiguration`; A-020's repository needs a `JdbcClient`, so `develop` has been red since that merge. Neither PR could have seen it — the test did not exist when A-020 branched. Same three-line fix as `ApplicationSmokeTest` and `ContractConformanceTest`.
- [x] **A-022** JWT access token, 15 min, claims `sub`, `role`, `permissions[]`, `projects[]`, `reportees[]`, `iat`, `exp`, `jti`.
  > `AccessTokenIssuer` (`api/feature/auth/`) mints; `JwtEncoderConfig` (`api/security/jwt/`) wires the single `JwtEncoder` bean, mirroring `PasswordEncoderConfig`. `AuthController` composes `AuthenticationService` (identity) with `AccessTokenIssuer` (token) rather than the two merging into one class — credential verification keeps its own tight timing/failure-shape contract, untouched by this task.
  > **HS256, symmetric secret — confirmed over RS256.** One process signs and, from A-032, verifies; nothing else needs to check a signature without holding the secret, and there is no key-rotation/vault story until A-075. `edutrack.jwt.secret` follows the `DB_PASSWORD`/`EMAIL_WEBHOOK_SECRET` pattern: a committed placeholder for `local`/CI, `JWT_SIGNING_SECRET` required everywhere else. Revisit if a separate verifier service ever appears.
  > **`sub` is the numeric user id, not the username.** Every other claim (`projects[]`, `reportees[]`) is already id-based, and A-034's `ScopeResolver` wants an id to compare against `assigned_to`, not a name to look up.
  > **Scope stays exactly what A-020 already resolved.** No new query — `AccessTokenIssuer` reads straight off `AuthenticatedUser`, which was shaped for this from the start.
  > **Not in this task:** the refresh cookie (A-023), rotation/family revocation (A-024), logout/blacklist (A-025), and verification itself — no route rejects a missing or expired token yet, that is A-032's filter chain.
- [x] **A-023** Opaque refresh token, 7 days, HttpOnly + Secure + SameSite=Strict cookie, `jti` in Redis, device-bound.
  > `RefreshTokenIssuer` mints, `RefreshTokenStore` persists, `AuthController` sets the cookie. All in `api/feature/auth/` rather than split into `api/security/` the way A-022 was — the `JwtEncoder` went to `security/jwt/` because A-032's filter chain will need a decoder from the same key, whereas every future caller of this store (A-024, A-025) is inside `feature/auth`.
  > **Redis holds `SHA-256(token)`, never the token.** The raw value exists in exactly two places: the `Set-Cookie` header and the browser's cookie jar. Redis persists to disk and gets backed up, so keying on the raw value would mean an RDB file — or one `KEYS *` during an incident — is seven days of live sessions. SHA-256 and not Argon2id: the input is 256 bits from `SecureRandom`, so there is no dictionary to slow down, and a password-grade KDF would put ~175 ms and 64 MB on every refresh for a threat that cannot exist. A-027's reset tokens want the same treatment.
  > **Redis and not a `refresh_tokens` table.** The key carries its own TTL, so expiry is the storage layer's job. A table needs a scheduled delete, and the day that job fails is the day expired sessions quietly keep working — invisible until audited.
  > **Device binding is User-Agent, deliberately not IP.** An IP-bound token logs honest users out several times a day — a phone moving wifi→cellular, a NAT pool rotating, a VPN reconnect — and the fix everyone reaches for is to stop enforcing it. A User-Agent is stable for as long as the browser is and changes precisely when the cookie has been replayed elsewhere. Stored hashed: equality is the only operation, and a plaintext UA is a fingerprinting datum sitting in a cache for a week. It is a weak binding and is not claimed to be more — an attacker with the cookie can copy the header too.
  > **`familyId` is stamped here, at login, though A-024 uses it.** A family is the chain of rotations descending from one login, so it is born at login; a token issued without one could never be joined to its siblings afterwards. One family per login, so revoking a compromised family ends *that* session rather than logging the user out everywhere.
  > **`Path=/api/v1/auth`, narrower than the contract's illustrative `Set-Cookie` line.** Only `/auth/refresh` and `/auth/logout` ever read it; scoping to `/` attaches a seven-day credential to every ticket list and attachment download, and to every proxy log along the way. Invisible to code — the cookie is `HttpOnly` and browser-managed — but **flagged for Debashis** as a deviation from `contracts/openapi.yaml`'s worked example, which shows no `Path`.
  > **An unreachable Redis shortens the session; it does not fail the login.** Same trade `RealtimeRelay` already made for the same dependency — failing would take the whole product down over a degradation confined to session length. It fails towards *less* access (15 minutes, then re-login), so nothing is weakened, only shortened. Logged at ERROR because a fleet in this state presents to users as "the app keeps logging me out", which is a support ticket rather than an alert.
  > **`secure-cookie: false` refuses to boot outside `local`** (`RefreshTokenConfig`, same posture as `DevNoAuthConfig`). The knob exists because Safari on `http://localhost` and any plain-http LAN address used to test on a real phone reject a `Secure` cookie outright, so those developers could not hold a session at all. Without the guard, someone eventually ships `false` — a defect with no error, no log line and no failing request.
  > **`SameSite=Strict` has a real cost, accepted.** A user arriving from a link in a notification mail cannot refresh on that first navigation and looks logged out until they navigate once inside the app. `Lax` avoids it and is what most sites pick; Strict is what makes CSRF against `/auth/refresh` structurally impossible rather than a thing a token has to defend against, which is worth one extra click on an internal tool.
  > **Not in this task:** `POST /auth/refresh` and rotation with family revocation (A-024), logout and the access blacklist (A-025), and *enforcement* of the device binding — the fingerprint is recorded but the only place it can be checked is the endpoint that does not exist yet. `StoredRefreshToken#matchesDevice` is that hook, present with its own test so A-024 does not have to reinvent it. Same shape as A-022, which minted a token nothing verified.
  > **`AuthLoginIT` gained a Redis container.** Without one the issuer degrades to no cookie and every A-023 assertion fails against a login that is working perfectly.
- [x] **A-024** 🔴 **Refresh rotation with family revocation** — reuse of a consumed token means theft: revoke the whole family, force re-login.
  > `RefreshRotationService` holds the sequence, `AuthController#refresh` is the route, and `RefreshTokenStore` grew the three primitives it needs. All in `api/feature/auth/`, following A-023.
  > **Deleting the old token on rotation is what makes reuse undetectable, and is the mistake the whole task turns on.** A deleted key and a key that never existed are the same absence, so a stolen token replayed *after* the victim's browser has rotated looks exactly like a typo — and §10.1's reuse rule becomes unenforceable with no symptom. Rotation therefore writes a `refresh-consumed:<sha256>` marker holding the family id, TTL'd to what remained of the token's own life. The marker is the memory that the token was real and spent.
  > **Family revocation is a tombstone, not a sweep.** When reuse is detected, the *other* members of the family are still live in Redis. Finding and deleting them needs a family→members index kept in step with every rotation, and the day it drifts a revoked token keeps working. `refresh-family-revoked:<familyId>` inverts that — nothing has to be found, and the check is positive: a family is usable only while nothing says it isn't. Its TTL is deliberately the full 7-day maximum rather than the family's real remaining life; a tombstone that expires *early* resurrects a family revoked for theft, and carrying the exact deadline would mean a second copy of an expiry that can disagree with the record.
  > **The claim is an atomic `DEL`, and that is the load-bearing line.** Two requests can carry one cookie — two tabs waking, or a retry of a refresh whose response was lost. Read-then-delete lets both through and forks one session into two. `DEL` reports whether it removed anything, so exactly one caller is ever told it won.
  > **The loser of that race is treated as reuse, and the honest double-submit pays for it.** Server-side a second presentation of a consumed token is indistinguishable from a replay, and §10.1 carves out no exception, so the family dies and the user re-logs in. The usual softener is a grace window — re-issue the successor if the reuse is within N seconds, same device — and it was **considered and not built**: it weakens the one guarantee this task exists to provide, and loosening later with evidence is far easier than tightening. **The frontend must single-flight its refresh** (one in-flight call, other callers await it) or a two-tab app will log itself out; that is the mitigation, and it belongs to whoever builds the interceptor.
  > **A device mismatch refuses the token but does *not* revoke the family — the deliberate asymmetry.** Chrome rewrites its `User-Agent` on every auto-update, which inside a seven-day window is close to routine; revoking on it would sign people out after a browser update and file it as theft. A control that fires on benign events gets switched off by whoever is on support that week. Refusing one token costs one re-login, the right price for a binding `StoredRefreshToken` openly calls weak — and a real thief copies the header anyway, so revoking here buys almost nothing against the actual threat. The presented token *is* discarded though, and that part matters: otherwise an attacker retries with one `User-Agent` after another until one matches and the fingerprint becomes a guessing game they win. Discarding caps it at one attempt, and costs the benign case nothing — a token whose recorded UA no longer matches was already permanently unusable.
  > **A-021's lockout is not consulted on refresh.** Refreshing is not a login. Honouring the lock would let any outsider end an employee's active session by typing a wrong password five times at their username — the protection becomes the attack. The lock governs the login form, where guessing happens.
  > **Expiry does not slide.** The successor inherits `expiresAt`, not a fresh seven days. Sliding expiry makes the session unbounded — a token used weekly never expires, and neither does a stolen chain kept warm — so the only thing that would ever end it is a logout, which an attacker has no reason to perform. The family gets a hard deadline set at login; the cost, accepted, is that an actively working user is signed out at day 7 rather than carried past it. **A-025's "absolute 12 h" tightens this and supersedes the 7-day bound.**
  > **Identity is re-read from the database on every refresh, not replayed from the stored record** (`AuthenticationService#resolveActiveUser`, `AuthUserRepository#findById`). A deactivation, a role change or a project reassignment lands at the next refresh — at most 15 minutes stale instead of seven days.
  > **Reuse is the one auth failure with its own `type` URI** (`refresh-token-reuse` vs `invalid-refresh-token`). Every other refusal in this package is uniform to deny an outsider information; this path is reachable only by someone holding a token we genuinely issued *and* consumed, so they already know it was real and the response tells them nothing. The gain is on the other side — the victim learns they were compromised, instead of seeing "session expired" and shrugging. Everything else (missing, expired, unknown, revoked family, wrong device, deactivated) shares one body.
  > **It fails closed in both directions.** Every write happens after the claim, so a failed marker or successor write ends the session rather than issuing anything. Read failures are **not** converted to 401: a 401 is a statement about the credential, and saying it because Redis blinked signs out the fleet and tells each of them, falsely, that their session was invalid. Those propagate as 5xx, which is retryable and leaves the cookie alone. Note this is the opposite of A-023's login degradation, and correctly so — there was a session to preserve there, here there is not.
  > **Every refusal clears the cookie.** Without it a browser holding a revoked-family token replays it forever: a 401 loop the user cannot break without clearing cookies by hand.
  > **Two contract deviations flagged for Debashis** rather than edited into `contracts/openapi.yaml` (Stream D's file), following A-023's precedent. The `/auth/refresh` `200` has no `Set-Cookie` header documented though the endpoint sets one, and the `401` does not mention that reuse carries a distinct `type`. Both are documented on the springdoc side; `ContractConformanceTest` compares path+verb only, so neither breaks the build.
  > **Not in this task:** logout and the access blacklist (A-025). A revoked family still leaves the last-issued *access* token valid for up to its remaining 15 minutes — nothing reads a blacklist yet and no filter chain exists (A-032). Until then "force re-login" means "issue nothing further", not "cut the current call off mid-flight". Worth stating plainly because it is the natural assumption on reading "revoke the whole family".
  > **Fixed a ~1%-flaky A-023 test** — `RefreshTokenIssuerTest.tokenValueIsOpaque` asserted a random 43-char base64url token `doesNotContain("42")`, which happens by chance about one run in a hundred and did so during this task. It tested the RNG, not the code; replaced with a decoded-length check that establishes the same property deterministically.
- [x] **A-025** Logout — delete refresh `jti`, blacklist access `jti` in Redis until natural expiry. Idle timeout 30 min, absolute 12 h.
  > `LogoutService` + `AccessTokenBlacklist` + `AuthController#logout` in `api/feature/auth/`; `JwtDecoderConfig` in `api/security/jwt/`; the two session bounds in `SessionProperties`, enforced in A-024's `RefreshRotationService`.
  > **Both halves of logout are required and each alone is a bug.** Deleting only the refresh token leaves the access token working for up to fifteen more minutes — on a shared machine that is fifteen minutes of someone else's session *after* they pressed Sign out, which is exactly the window the user believes they just closed. Blacklisting only the access token leaves the cookie able to mint a new one on the next tick, so the logout undoes itself.
  > **`JwtDecoderConfig` is new, and A-022 predicted the wrong first caller.** A-022 assumed A-032's filter chain would be the first thing to *read* an access token; `/auth/logout` got there first, because it is the only endpoint the contract does not mark `security: []`. The decoder is therefore proper wiring in `security/jwt/` rather than parsing inside a controller — A-032 consumes this same bean instead of introducing a second one on the same key. `macAlgorithm(HS256)` is pinned explicitly: without it Nimbus honours whatever algorithm the token's own (attacker-controlled) header names. Expiry and issuer are the decoder's validators, not a caller's `Instant` comparison — the same omission that is a small bug here is a total auth bypass in A-032.
  > **Verification has to be real, not a decode.** Accepting an unsigned token would make this an endpoint for logging *other people* out: forge any `jti`, blacklist a stranger's access token. `AuthLogoutIT` asserts a forged token revokes nothing and deletes nothing.
  > **Logout does not revoke the family, and that is the single most important absence here.** Signing out of a laptop must not sign the user out of their phone. Family revocation is A-024's response to *theft*; reusing it for an ordinary sign-out makes the two indistinguishable in the logs and in the user's experience. Tested from both directions — the other device still refreshes, and no tombstone is written.
  > **`discard()`, never `claim()` + `markConsumed()`.** A consumed marker is precisely what turns a later presentation into *detected reuse*, so recording one at logout would mean a stale tab retrying after sign-out revokes the whole family for something that was never theft. `AuthLogoutIT` pins the resulting `type` as `invalid-refresh-token`, not `refresh-token-reuse`.
  > **The access token is mandatory; the refresh cookie is not.** The asymmetry is deliberate: the access token is *how we know whose session to end*, while the cookie merely names a token to delete. The people most in need of a working Sign out are those whose session is already half-broken — cookie expired, already rotated, or withheld by `SameSite=Strict` on that navigation. Refusing them would leave the access token live, which is the one outcome logout must never produce. Idempotent for the same reason: every failure mode here leaves someone logged in who asked not to be.
  > **The blacklist TTL is the token's own remaining life, which is what keeps it self-limiting.** An entry only has to outlive the token it revokes; a second later the token is refused as expired anyway. So the blacklist can never hold more than one access-token-lifetime of logouts however many people sign out, and needs no sweeper. A fixed or generous TTL grows without bound and eventually becomes the thing that pages someone. Keyed on `jti` — already a random UUID and useless to whoever holds it — not on the token, which is a bearer credential and must not sit in a cache that gets snapshotted.

  - 🔴 **`oauth2ResourceServer` exempts anything carrying `Authorization: Bearer` from CSRF, ours included.** So `POST /auth/logout` with a bearer token succeeds with no token whatsoever — measured on a cookie-less client, not assumed. It looks exactly like the hole that was just closed. It is not one: a cross-origin page cannot set that header, so every request an attacker can actually forge arrives without it and is checked. The property to hold onto is not "every request is checked" but "every request an attacker can produce is checked". Two consequences: the SPA's logout needed no change, and `/auth/refresh` — called by the startup refresh with no access token in hand — is the one route where the client genuinely has to send the header.
  - **The CSP is computed, not written down, in the two places a constant would rot.** The inline-script hash is taken from the `index.html` that is actually served, so D-15's pre-paint theme script keeps working and Vite is free to minify it; a hardcoded `'sha256-…'` fails as a blank application in production with a green suite, because nothing in a unit test parses CSP. The object-store origin comes from `ObjectStorageProperties`, because §4B.4 hands attachments out as presigned URLs on MinIO or S3 — a different origin, and a different one per deployment.
  - **`style-src` keeps `'unsafe-inline'`, and that is stated rather than quietly omitted.** Every Radix dialog, popover and select depends on `react-remove-scroll`, which injects a `<style>` element at runtime and exposes no nonce API. "We have a strict CSP" and "our CSP allows unsafe-inline styles" are both true, and only the first is usually said. `script-src` is the one that matters and it allows neither `'unsafe-inline'` nor `'unsafe-eval'` — pinned by a test, because relaxing it is the reflex when something breaks.
  - **An unparseable object-store endpoint drops the source rather than emitting it.** A browser discards an entire policy it cannot parse, so one malformed source expression would not merely fail to allow attachments — it would silently remove every protection in the header, which is the worst available outcome and the one nobody would notice.
  - **The password-change throttle is a second budget, deliberately, not a reuse of A-021's lockout.** `PasswordChangeService` has said since A-026 that feeding these failures into the login counter would let somebody holding a stolen token lock the real owner out of signing in — turning the defence into the attack, on demand. So it keeps its own budget keyed on the *user id*, which is knowable here because the endpoint is behind `isAuthenticated()`. That also means it needs only one dimension, where `LoginRateLimiter` needs two: login cannot tell one caller from another except by address, and this can. Five in fifteen minutes rather than login's seven, spent on wrong guesses only — a correct change costs nothing and clears the count.
  - **springdoc is closed by default and opened where something needs it**, which turned out to be three places: the `local` profile (`make api` advertises Swagger UI), the api module's test-scope properties (`ContractConformanceTest` fetches `/v3/api-docs` from the running app, and `SecurityChainIT` asserts it is public), and nothing else — the CI packaging job runs the jar with `--spring.profiles.active=local`, so its 200 check passes unchanged.   - **Dependency scanning is split by event, and that split is the design.** Pull requests get `dependency-review`, which diffs manifests against the base and can therefore only fail on something the author did. The full OSV + `npm audit` sweep runs nightly and on pushes, never on a PR. The obvious alternative — scan everything on every PR — makes a CVE published at 3am against an unrelated transitive dependency fail the next six PRs, none of which caused it or can fix it, and CLAUDE.md already records where that ends: *a verification step nobody can afford is a verification step nobody performs*.

The application image belongs to A-075, which is the task that will create one.   > **Counting failures rather than attempts in the spray set is what keeps the NAT problem from returning.** Capping distinct usernames *attempted* per source would punish the shared-office case exactly as the withdrawn per-IP limiter did: two hundred people behind one gateway are two hundred distinct usernames before anything has gone wrong. Honest traffic contributes nothing to this budget, however much of it there is — proven by a test that runs 21 consecutive successful logins and asserts the source is still unthrottled.

This is precisely the distinction A-021's 423 cannot make: that one is a statement about the *account*, so it must follow the password check. This one is a statement about the *caller*.

A test asserts `MAX_PER_PAIR > 5`, so lowering it below the lockout fails the suite rather than silently ensuring no account ever locks and no admin is ever told.
