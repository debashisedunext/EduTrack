  - **Both halves, and the server one is the guarantee.** The picker filtering and the asterisks stop somebody choosing what will be refused; `ProjectSettingsGate` on `POST /tickets` is what makes the setting true, and it reads `projects.mandatory_fields` and `project_task_types` directly inside the creation transaction — `ClientGate` and `ModuleGuard` next door read Stream B's tables the same way. An HTTP call to `getProjectSettings` instead would buy a network hop, a second failure mode and a race against the settings changing mid-request; two `SELECT`s inside the transaction mean the settings that are read are the settings in force when the row lands.
  - **An empty allow-list is unrestricted, and getting that backwards would stop ticket creation organisation-wide.** Every project has no `project_task_types` rows until somebody configures one, so the wrong reading is also the universal one. Restated in `ProjectTicketRules.taskTypeRefused`, in `ProjectRules.allowedTaskTypeIds` as `null`-not-empty-set, and pinned by a test on each side.
  - **Refused before the sequence moves.** Both checks run ahead of `nextTicketCode`, and the planned close date is now resolved there too — a number burnt on a rejected request is a permanent gap in that project's ticket codes. `TicketWriteIT` asserts `ticket_seq` is unchanged after each refusal.
  - **`saveAsDraft` does not waive the project's fields**, where C-013's draft waives the description, the estimate and §4B.2's client rule. Those three are the blueprint's rules about what a ticket ought to say and a draft exists to hold one that cannot say them yet. These are a *project's* rules, and `saveAsDraft` is accepted by the server and acted on nowhere — a draft is stored as an ordinary ticket today, so waiving on the flag would hand every caller a one-field opt-out producing a ticket indistinguishable from any other. The paragraph to revisit when a draft becomes a real server-side state is on `ProjectSettingsGate`.
  - **`PLANNED_CLOSE_DATE` is measured against the resolved date, not against what the caller sent**, and is deliberately not a form rule at all. Overriding the date is PM and Admin only, so S-19 renders the control read-only for the other four roles — requiring the caller to send one would make it the single setting four of six roles could never satisfy. It fails exactly when the ticket really would have none: no override and no rung of the SLA ladder answering.
  - **Not applied on `PATCH`.** A newly-ticked mandatory field would otherwise make every existing ticket on the project un-editable, including ones closed years ago, and `PatchRequest` carries seven of the ten fields so most could not be filled in through that route anyway. The setting governs what may be raised, not what was.
  - **A disallowed task type is filtered out of the picker, where an ineligible client is shown and refused.** The two are opposite for opposite reasons: a client blocked by B-028 is an obstacle the person raising the ticket can usually go and fix, while a project's allow-list is a deliberate configuration only a PM or Admin can change, on a screen most of the six roles cannot open. Offering it would be offering a refusal. The hint says the list is restricted, because a picker that is simply shorter than it was on the last project reads as a list that has lost its data.
  - **The task-type `Select` is now `''`-controlled rather than `undefined`-controlled.** Clearing a type the newly-picked project does not accept left Radix displaying the old label — it reads `undefined` as *uncontrolled* and keeps its own state — so the form looked empty while still holding an id the picker no longer offered. That is the invisible stale value the clearing exists to prevent, and it also silences the "changing from uncontrolled to controlled" warning the first selection used to emit.
  - **The form cannot enforce a rule it has not been told about yet, and that is left as it is.** `GET /projects/{id}/settings` is a round trip that starts when the project is picked; a save fired inside that window validates against no project rules and the server refuses it, mapping the 400 back onto the fields. Unreachable by a person with a title and a description still to type, trivially reachable by `fireEvent` — which is why the tests wait on the asterisk rather than the form disabling its own save buttons for a moment on every project change.

Client regenerated; the diff is doc comments in four files. Flagged rather than done quietly, C-015/C-019's precedent.
  - **The CRM fixture requires `MODULE` and `ESTIMATED_HRS`**, and almost every test in `CreateTicketPage.test.tsx` raises its ticket on CRM — so the suite's `beforeEach` now clears it and the C-071 block puts it back explicitly. Left in place, a project rule would sit on top of whichever rule each test is actually measuring and assertions would pass for reasons unrelated to their subject; the C-068 module test was already doing exactly that.

All three now go through `selectableLevels`.
  - **The filter is in the client, not in the query parameter.** Passing nothing and filtering `isActive !== false` locally makes all three screens correct under either endpoint default, which is what lets Stream B widen `listPriorities` to match `listTaskTypes` and `listModules` as a change of their own with no coordination — the widening this row was waiting on. `isActive !== false` rather than `=== true`, because the field is optional on the contract's `Priority` and treating silence as "retired" would empty every picker.
  - **`TicketLevelControl` keeps the ticket's own level whatever the master now says**, via a second function rather than a flag. Retiring CRITICAL does not move the tickets already at CRITICAL; filtering flat would open S-20's dialog with no radio checked — which reads as "this ticket has no level" — and make "I opened this by mistake" unavailable, since the only way out would be changing to something else. Appended, not inserted: a retired row has no place in a sequence it has left.
  - **The list filter drops retired levels; the module filter beside it deliberately does not.** C-070 argued a *module* filter must keep retired rows, because "every open Transport ticket" is a fair question about a module being wound down. A level filter is the other case, and `listStatuses` already states the reasoning for the status filter next to it — the endpoint is active-only today, so this is the set that filter has always shown, and the same list also feeds the bulk **Change level** dialog, which is a picker in the plainest sense.   - **The task type's `defaultLevel` is guarded too.** `TaskTypeService` refuses a retired level as a default so the masters should agree, but they reach the form as two independent queries that go stale independently — and a pre-filled level the picker does not show renders as a blank form, cannot be corrected by clicking, and is then refused on submit for a level nobody chose.
