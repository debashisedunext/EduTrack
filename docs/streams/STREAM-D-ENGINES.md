## Infrastructure — weeks 3–5

- [x] **D-010** 🔴 **Outbox worker pattern** — claim rows with `SELECT … FOR UPDATE SKIP LOCKED`, send, stamp the result. `email_log` **is** the queue: `status ∈ {QUEUED, SENT, BOUNCED, FAILED}`, `retry_count`, plus a `next_attempt_at` column for backoff. Enqueue is atomic with the business transaction, so a rolled-back handoff cannot leave a phantom mail queued. *(Replaces BullMQ — PLAN.md §2.2)* — *`worker/outbox/` + `domain/outbox/OutboxEnqueuer`; claim leases via `next_attempt_at` rather than adding a fifth `status`; no ShedLock by design, `SKIP LOCKED` is what allows horizontal scaling. `OutboxWorkerIT` proves disjoint concurrent claims, backoff, retry exhaustion and rollback atomicity against MySQL 8.4. Transport defaults to `logging` until D-029 renders bodies.*
- [x] **D-011** `@Scheduled` + **ShedLock** (Redis or JDBC provider) so scanners don't double-fire across instances. — *`worker/scheduling/SchedulerLockConfig`. **Redis provider**, not JDBC: the JDBC one needs its own `shedlock` table and therefore a Stream A migration, for a lock holding no business data. `defaultLockAtMostFor` PT10M, overridable per scanner. The outbox is deliberately left unlocked — `SKIP LOCKED` is what lets it scale horizontally. `SchedulerLockIT` proves two instances exclude, release, and that a crashed instance's lock expires.*
- [x] **D-012** Spring WebSocket + STOMP config, Redis pub/sub relay for multi-instance fan-out. *(Replaces Socket.IO)* — *`api/realtime/`. Endpoint `/ws` with SockJS; broker prefixes `/topic`, `/queue`, app `/app`, user `/user`. `RealtimePublisher` always goes out via Redis — never straight to the local broker — so every instance delivers by one path and the originating instance cannot double-send. Delivery is best-effort by design; anything the user must not miss is persisted by D-046. `RealtimeRelayIT` uses a real STOMP client and proves same-instance delivery, cross-instance fan-out, destination isolation and that a malformed relay message doesn't kill the listener. Destination naming is D-014; subscription authorisation is D-013.*
- [x] **D-013** 🔴 **Channel interceptor authorising subscriptions with the same scope rules as REST** — a Developer must not be able to subscribe to a ticket topic they could not `GET`. This is the socket-layer equivalent of the scope guard and is easy to forget. — *`SubscriptionAuthorisation` on the **client inbound channel**, so a SUBSCRIBE is judged before the broker registers it — filtering outbound would leave the subscription in place and re-check on every delivered message. **Until this landed, chat's whole authorisation model could be walked around by opening a socket**: the REST side makes a thread you are not in indistinguishable from one that does not exist, and then broadcast every message to `/topic/ticket.{id}`, which anyone could subscribe to. **Deny by default** — an unparseable or unknown destination is refused, so a room added later without a rule fails loudly rather than being world-readable. **Refusals throw rather than drop**: returning null would swallow the SUBSCRIBE and leave the client believing it was subscribed and receiving nothing, the exact silent failure D-014 exists to prevent. The message names only the destination, so a probe learns nothing — same reasoning as 404-not-403. `SubscriptionScope` is an **interface implemented per feature and unioned**, because the answer belongs to whoever owns the data: `ChatSubscriptionScope` grants a room you have a thread in (no `ScopeResolver` needed — `chat_participants` is explicit), and A-034 arrives later as a second implementation without changing this class. **Stage and manager topics are shut until A-034** — a stage queue open to everyone is a list of who is working on what across the organisation. *(D-059 later opened the stage topic — not by using `ScopeResolver`, but by making the frame carry no ticket, which turns the question into project membership. The manager topic is still shut.)* **Found a latent D-015 bug:** the frontend built `/user/{id}/queue/events` for *subscribing*, but that is the server's send form — Spring resolves a subscription to it as a literal destination nothing publishes to, so it would have been accepted, silent and dead forever. Replaced with `ownQueue()`, which takes no id because Spring scopes it to your session; the interceptor refuses the id-bearing form so the mistake is loud. **Depends on the dev-principal fix (PR #46)** — a subscription cannot be authorised against a principal that never arrives. `RealtimeRelayIT` now has to satisfy the guard to do its own job, which makes it a second independent proof that the principal survives the handshake and that the interceptor is wired. **A scope that cannot answer now grants nothing and vetoes nothing**, which cost a red CI to learn: `ChatSubscriptionScope` queries the database on every SUBSCRIBE, this IT deliberately starts no MySQL, and it passed on any machine with something listening on 3306 while failing on the runner — the exception came out of `preSend` and refused every room, including ones a healthy scope was granting, with nothing logged to say why. Since the union only ever grants, swallowing a scope's failure can only make the decision more restrictive. The IT also stopped sleeping 300 ms and now proves delivery before asserting (a RECEIPT would be the obvious fix and the simple broker never sends one), which repaired the destination-isolation test — it had been asserting that nothing arrived on a subscription CI never registered. 12 tests in `SubscriptionAuthorisationTest`.*
- [x] **D-014** Destination map per blueprint §9.3 — `/user/{id}/queue/events`, `/topic/ticket.{id}`, `/topic/stage.{code}.{projectId}`, `/topic/project.{id}`, `/topic/manager.{id}`. — *`api/realtime/RealtimeDestinations`, plus a sealed `RealtimeDestination` and `parse()` — the inverse D-013 authorises against, so the interceptor never re-derives room identity with an ad-hoc substring. - [x] **D-015** Frontend STOMP client (`@stomp/stompjs` + SockJS fallback) with reconnect and subscription lifecycle. — *`frontend/src/realtime/`. One shared socket per tab; `useRealtime(destination, handler)` is the whole API. **stompjs restores the socket but not the subscriptions**, so every room is re-subscribed on every connect — without that the app reconnects, looks healthy, and silently never receives anything again. ## M5 — SLA, escalation & mail · weeks 6–11

### Scanners
- [x] **D-020** 🔴 **SLA scanner, every 15 minutes** — `pcd_open < now` → level `CRITICAL`, `is_delayed = true`, `delayed_since` stamped, alert to Reporting Manager + PM + assignee. Uses A's generated-column index so the scan is O(breaches), not O(all tickets). — *`worker/sla/`. **Detection is a timestamp comparison and reporting is not** — the Planned Close Date is an instant somebody committed to, so it passes when it passes; running *detection* through working hours would mean a Friday-18:00 deadline was not breached until Monday, which is not what the client was promised. The scan leans on A-009's `pcd_open`: the STORED generated column is NULL once a ticket closes, so closed rows leave the index range entirely rather than being filtered out of a full scan. `is_delayed = 0` sits in the WHERE of both the select **and** the update, so a ticket escalates once instead of re-alerting every fifteen minutes until somebody closes it, and the update's rowcount is what decides whether this pass is the one that announces it. **`SlaEscalation` is a separate bean, and that is load-bearing**: `@Transactional` is proxy-applied, so calling it from another method of the scanner would have run every escalation with no transaction at all, silently — the flag, the bell entries and the queued mail have to commit together. Recipients are a `LinkedHashSet` because a PM who assigned a ticket to themselves is routine and three copies of one breach is how people learn to filter the alert. Deactivated recipients keep the bell entry and get no mail: their address may have been reassigned, and a plausible undeliverable address turns D-033's delivery log into noise. `lockAtMostFor` is close to the interval deliberately — a lock released early double-alerts, one held too long only delays a pass, and those costs are not symmetric. Capped at 500 per pass with the remainder logged, because a silent cap reads as "nothing else was wrong". 10 tests in `SlaScannerIT`.*
- [x] **D-021** 80%-of-SLA pre-breach warning to the assignee. — *`worker/sla/PreBreachScanner`. **The only alert in the engine that can change the outcome** — D-020 reports what has already gone wrong to three people; this tells one person it is about to, which is why it goes to the assignee alone. Copying their manager turns a helpful nudge into being reported on, and the escalation chain already fires if the date actually passes. The proportion is working hours elapsed over working hours **committed** (`date_reported` → `planned_close_date`), both from B-024: 80% of a wall-clock window lands in the wrong place for anything spanning a weekend, which is most windows longer than a few days. **Claimed once per `(ticket_id, cycle_no)`, not per ticket** — a reopen starts a new window and must re-arm, or the warning stops arriving for exactly the tickets that have already gone wrong once. Unlike D-023 there is **no cheap SQL prefilter**: both sides of the ratio are working hours and the wall-clock ratio bounds it in neither direction, so the query narrows to open, assigned, unbreached, unwarned and the calendar decides the rest. A window entirely inside non-working time returns early rather than dividing by zero. `SLA_80_PERCENT_ELAPSED` is an ESCALATION in the catalogue, so D-036 makes the mail unsuppressable — which follows from the category rather than being decided here, and is the right side to err on for an alert whose whole value is that it arrives. 9 tests; the weekend case is **mutation-checked** and its first draft was rewritten after the mutation passed — wall-clock and working hours both fell under the threshold, so it proved nothing.*
- [x] **D-022** Stale-task nudge — no update for 3 working days, to assignee cc RM. — *`worker/sla/StaleTicketScanner`. The other three scanners are about deadlines; this one is about **silence**, which is a different failure — a ticket can be nowhere near its Planned Close Date, in the right stage with the right owner, and simply forgotten. **Activity deliberately does not mean `tickets.updated_at`.** That column moves on any write to the row including D-020's own `is_delayed` stamp, so a breached ticket would read as freshly updated and *escalating* a ticket would be the thing that stopped anybody being nudged about it — the two engines silently cancelling on exactly the tickets already in trouble. Activity is therefore a person doing something: a comment, an effort log or a stage hop, floored at `date_reported`. There is a test that escalates a ticket and asserts it is still nudged. **The nudge repeats** where D-021's warning does not — a ticket still untouched three working days later is stale again, and a reminder sent once and never repeated is one that gets ignored once — so the table is one row per ticket updated in place, with no `cycle_no`, because staleness is a property of the ticket now rather than a commitment per cycle. Three working *days* is derived from the calendar's `workDayLength()` rather than written as 27 hours, or a seven-hour-day org would quietly get "nearly four days". Hourly, not quarter-hourly: the threshold is in days. Adds `STALE_TICKET_NUDGE` to the catalogue as `OTHER`, so D-036 leaves it **opt-out** — a reminder nobody can switch off is how a mailbox rule gets written that hides the alerts that matter. **Found a real claim bug:** Connector/J reports matched rather than changed rows, so an `ON DUPLICATE KEY UPDATE` with the freshness test in an `IF()` returned 1 even when it changed nothing and nudged on every pass; split into `INSERT IGNORE` plus a conditional `UPDATE … WHERE`, where the count is unambiguous. 10 tests.*
- [x] **D-023** 🔴 **Stage-SLA scanner, separate from ticket SLA** — a ticket can be well inside its PCD while rotting four days in the Deployment queue. Per-stage SLAs are what make the ribbon actionable rather than decorative. *(§16 item 3b)* — *`worker/sla/StageSlaScanner`. **A second scanner, not a branch in D-020**: the two answer different questions, alert different people (the *stage owner*, not the ticket assignee — the person who can unstick it is whoever it was handed to), and remember what they announced in different places. That last one is the interesting constraint: `ticket_stage_transitions` is append-only and A-008 permits exactly one mutation, sealing, so there is nowhere to put an "alerted" flag. The fact lives in its own `stage_sla_alerts` table keyed on the **transition**, not the ticket — a DEV → QA → DEV loop is three segments that can each breach separately — and `INSERT IGNORE` against the primary key makes the claim atomic without a lock. **The SQL prefilter is exact, not a guess**: working hours are never greater than wall-clock hours, so `TIMESTAMPDIFF(SECOND, entered_at, now) >= sla_hours * 3600` can only be too permissive, never too strict, and the calendar is consulted for the survivors. Computed per row against each stage's own budget — one `now - N hours` cutoff would apply one stage's SLA to all of them — and in seconds rather than `INTERVAL … HOUR`, which would truncate a 1.5-hour SLA to one. `sla_hours` is denominated in working hours, so the elapsed side is too (D-027); the test hands a ticket to QA on Friday evening with a 4-hour budget and asserts it has **not** breached by Monday morning, and **mutation-checking** confirms wall-clock maths fails it. 11 tests.*
- [x] **D-024** Escalation matrix per project — L1 at breach, L2 after 48 h beyond PCD to the RM's manager. — *`worker/sla/EscalationPolicies` + `L2EscalationScanner`. **The matrix already existed** — A-007's `sla_policies(project_id, task_type_id, level, …, escalate_to_l1, escalate_to_l2)` — so this task is about *using* it, and the two columns are **flags, not recipients**: the schema names who each level means (L1 the reporting manager, L2 that manager's manager) and the matrix only says whether the level applies to this kind of ticket on this project. L1 gates only the reporting manager — the assignee owns the work and the PM owns the project, so switching off an escalation must not switch off the alert. **48 hours is 48 *working* hours**, a bit over five working days on a nine-hour calendar rather than two: an escalation that fires over a weekend reaches a manager about a ticket their team had no chance to touch. `is_delayed` is the entry condition rather than a second date comparison, so L2 cannot disagree with L1 about whether the first level ever fired. A ticket whose chain runs out is **claimed with a null target and logged**, or every pass forever re-evaluates a ticket nobody can be told about. 12 tests, plus 2 added to `SlaScannerIT` for the L1 gate.*
- [x] **D-025** Ping-pong flag at `iteration_no ≥ 3` → PM dashboard. — *`V20260811_1100__ping_pong_flags.sql`; `worker/sla/PingPong{Repository,Flag,Scanner}`. **The table records who has been told, not the condition** — `tickets.current_iteration >= 3` already answers "which tickets are ping-ponging", and A-058's widget can read either; what it cannot do without this is avoid announcing the same bounce every hour forever. ### Mail engine — §4B.6
- [x] **D-029** Thymeleaf templates driven by Stream B's notification template master, with merge tags `{{ticket_id}}`, `{{assignee}}`, `{{stage}}`, `{{client}}`, `{{planned_close}}`. — *`worker/outbox/MailRenderer`. **Until this landed `SmtpMailTransport` sent the subject line as the body** — every §4B.6 mail was one sentence with no ticket, no link and nothing to act on. **Two substitutions, and only one escapes**: the body is HTML carrying user text (ticket titles, client names, handoff comments), so its values are HTML-escaped with no opt-out — an "allow HTML in this tag" switch would be a stored-XSS feature request with a friendly name, aimed at client contacts outside the org. The subject is not HTML and is escaped as nothing, or every mail would carry a literal `&amp;`. Ampersand is replaced first, or `<` becomes `&amp;lt;`. **A tag with no value renders as nothing, never as its own braces**: an internal ticket has no client, and printing `{{client}}` would deliver at send time exactly the failure B-022's save-time validation exists to prevent, where no Admin can see it. An *unknown* tag is left visible instead — B-022 refuses to save one, so it was written around the screen, and blanking it would hide the mistake. **Falling back is not an error path**: no template, an inactive one, or an unseeded event still sends with the subject as the body, because §7.7 calls mail the guaranteed channel and "guaranteed unless somebody deactivated a template" is not a guarantee. Values go through `Matcher.quoteReplacement` — currency in a ticket title is routine, and `$` is a group reference otherwise. The layout is deliberately 2004-era table HTML with inline styles: Outlook renders with Word's engine and Gmail strips `<head>`. `th:utext` appears once, on the already-escaped body, and nothing else in that file may use it. Mail is now multipart/alternative so a text-only client gets the subject rather than markup. 13 tests; D-030 fills in the chrome.*
