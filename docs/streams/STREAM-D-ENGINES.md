## Infrastructure — weeks 3–5

- [x] **D-010** 🔴 **Outbox worker pattern** — claim rows with `SELECT … FOR UPDATE SKIP LOCKED`, send, stamp the result. `email_log` **is** the queue: `status ∈ {QUEUED, SENT, BOUNCED, FAILED}`, `retry_count`, plus a `next_attempt_at` column for backoff. Enqueue is atomic with the business transaction, so a rolled-back handoff cannot leave a phantom mail queued. *(Replaces BullMQ — PLAN.md §2.2)* — *`worker/outbox/` + `domain/outbox/OutboxEnqueuer`; claim leases via `next_attempt_at` rather than adding a fifth `status`; no ShedLock by design, `SKIP LOCKED` is what allows horizontal scaling. `OutboxWorkerIT` proves disjoint concurrent claims, backoff, retry exhaustion and rollback atomicity against MySQL 8.4. Transport defaults to `logging` until D-029 renders bodies.*
- [x] **D-011** `@Scheduled` + **ShedLock** (Redis or JDBC provider) so scanners don't double-fire across instances. — *`worker/scheduling/SchedulerLockConfig`. **Redis provider**, not JDBC: the JDBC one needs its own `shedlock` table and therefore a Stream A migration, for a lock holding no business data. `defaultLockAtMostFor` PT10M, overridable per scanner. The outbox is deliberately left unlocked — `SKIP LOCKED` is what lets it scale horizontally. `SchedulerLockIT` proves two instances exclude, release, and that a crashed instance's lock expires.*
- [x] **D-012** Spring WebSocket + STOMP config, Redis pub/sub relay for multi-instance fan-out. *(Replaces Socket.IO)* — *`api/realtime/`. Endpoint `/ws` with SockJS; broker prefixes `/topic`, `/queue`, app `/app`, user `/user`. `RealtimePublisher` always goes out via Redis — never straight to the local broker — so every instance delivers by one path and the originating instance cannot double-send. Delivery is best-effort by design; anything the user must not miss is persisted by D-046. `RealtimeRelayIT` uses a real STOMP client and proves same-instance delivery, cross-instance fan-out, destination isolation and that a malformed relay message doesn't kill the listener. Destination naming is D-014; subscription authorisation is D-013.*
- [x] **D-013** 🔴 **Channel interceptor authorising subscriptions with the same scope rules as REST** — a Developer must not be able to subscribe to a ticket topic they could not `GET`. This is the socket-layer equivalent of the scope guard and is easy to forget. — *`SubscriptionAuthorisation` on the **client inbound channel**, so a SUBSCRIBE is judged before the broker registers it — filtering outbound would leave the subscription in place and re-check on every delivered message. **Until this landed, chat's whole authorisation model could be walked around by opening a socket**: the REST side makes a thread you are not in indistinguishable from one that does not exist, and then broadcast every message to `/topic/ticket.{id}`, which anyone could subscribe to. **Deny by default** — an unparseable or unknown destination is refused, so a room added later without a rule fails loudly rather than being world-readable. **Refusals throw rather than drop**: returning null would swallow the SUBSCRIBE and leave the client believing it was subscribed and receiving nothing, the exact silent failure D-014 exists to prevent. The message names only the destination, so a probe learns nothing — same reasoning as 404-not-403. `SubscriptionScope` is an **interface implemented per feature and unioned**, because the answer belongs to whoever owns the data: `ChatSubscriptionScope` grants a room you have a thread in (no `ScopeResolver` needed — `chat_participants` is explicit), and A-034 arrives later as a second implementation without changing this class. **Stage and manager topics are shut until A-034** — a stage queue open to everyone is a list of who is working on what across the organisation. **Found a latent D-015 bug:** the frontend built `/user/{id}/queue/events` for *subscribing*, but that is the server's send form — Spring resolves a subscription to it as a literal destination nothing publishes to, so it would have been accepted, silent and dead forever. Replaced with `ownQueue()`, which takes no id because Spring scopes it to your session; the interceptor refuses the id-bearing form so the mistake is loud. **Depends on the dev-principal fix (PR #46)** — a subscription cannot be authorised against a principal that never arrives. `RealtimeRelayIT` now has to satisfy the guard to do its own job, which makes it a second independent proof that the principal survives the handshake and that the interceptor is wired. **A scope that cannot answer now grants nothing and vetoes nothing**, which cost a red CI to learn: `ChatSubscriptionScope` queries the database on every SUBSCRIBE, this IT deliberately starts no MySQL, and it passed on any machine with something listening on 3306 while failing on the runner — the exception came out of `preSend` and refused every room, including ones a healthy scope was granting, with nothing logged to say why. Since the union only ever grants, swallowing a scope's failure can only make the decision more restrictive. The IT also stopped sleeping 300 ms and now proves delivery before asserting (a RECEIPT would be the obvious fix and the simple broker never sends one), which repaired the destination-isolation test — it had been asserting that nothing arrived on a subscription CI never registered. 12 tests in `SubscriptionAuthorisationTest`.*
- [x] **D-014** Destination map per blueprint §9.3 — `/user/{id}/queue/events`, `/topic/ticket.{id}`, `/topic/stage.{code}.{projectId}`, `/topic/project.{id}`, `/topic/manager.{id}`. — *`api/realtime/RealtimeDestinations`, plus a sealed `RealtimeDestination` and `parse()` — the inverse D-013 authorises against, so the interceptor never re-derives room identity with an ad-hoc substring. Stage codes are validated, not sanitised: a dot would re-shape the destination and could land a subscriber in another team's queue. Unknown destinations parse to empty and must be denied, never defaulted.*
- [x] **D-015** Frontend STOMP client (`@stomp/stompjs` + SockJS fallback) with reconnect and subscription lifecycle. — *`frontend/src/realtime/`. One shared socket per tab; `useRealtime(destination, handler)` is the whole API. **stompjs restores the socket but not the subscriptions**, so every room is re-subscribed on every connect — without that the app reconnects, looks healthy, and silently never receives anything again. Rooms are ref-counted, so three components watching one ticket open one subscription and the first unmount does not close it for the others. `destinations.ts` mirrors D-014's Java map because a mistyped destination is accepted by the broker and delivered to nobody. Transport is loaded on first subscribe, keeping ~170 kB of SockJS out of the initial chunk. Verified against the real `/ws`: SockJS handshake, STOMP session, subscription accepted. Not authorised yet — that is D-013.*

## M5 — SLA, escalation & mail · weeks 6–11

### Scanners
- [x] **D-020** 🔴 **SLA scanner, every 15 minutes** — `pcd_open < now` → level `CRITICAL`, `is_delayed = true`, `delayed_since` stamped, alert to Reporting Manager + PM + assignee. Uses A's generated-column index so the scan is O(breaches), not O(all tickets). — *`worker/sla/`. **Detection is a timestamp comparison and reporting is not** — the Planned Close Date is an instant somebody committed to, so it passes when it passes; running *detection* through working hours would mean a Friday-18:00 deadline was not breached until Monday, which is not what the client was promised. The scan leans on A-009's `pcd_open`: the STORED generated column is NULL once a ticket closes, so closed rows leave the index range entirely rather than being filtered out of a full scan. `is_delayed = 0` sits in the WHERE of both the select **and** the update, so a ticket escalates once instead of re-alerting every fifteen minutes until somebody closes it, and the update's rowcount is what decides whether this pass is the one that announces it. **`SlaEscalation` is a separate bean, and that is load-bearing**: `@Transactional` is proxy-applied, so calling it from another method of the scanner would have run every escalation with no transaction at all, silently — the flag, the bell entries and the queued mail have to commit together. Recipients are a `LinkedHashSet` because a PM who assigned a ticket to themselves is routine and three copies of one breach is how people learn to filter the alert. Deactivated recipients keep the bell entry and get no mail: their address may have been reassigned, and a plausible undeliverable address turns D-033's delivery log into noise. `lockAtMostFor` is close to the interval deliberately — a lock released early double-alerts, one held too long only delays a pass, and those costs are not symmetric. Capped at 500 per pass with the remainder logged, because a silent cap reads as "nothing else was wrong". 10 tests in `SlaScannerIT`.*
- [x] **D-021** 80%-of-SLA pre-breach warning to the assignee. — *`worker/sla/PreBreachScanner`. **The only alert in the engine that can change the outcome** — D-020 reports what has already gone wrong to three people; this tells one person it is about to, which is why it goes to the assignee alone. Copying their manager turns a helpful nudge into being reported on, and the escalation chain already fires if the date actually passes. The proportion is working hours elapsed over working hours **committed** (`date_reported` → `planned_close_date`), both from B-024: 80% of a wall-clock window lands in the wrong place for anything spanning a weekend, which is most windows longer than a few days. **Claimed once per `(ticket_id, cycle_no)`, not per ticket** — a reopen starts a new window and must re-arm, or the warning stops arriving for exactly the tickets that have already gone wrong once. Unlike D-023 there is **no cheap SQL prefilter**: both sides of the ratio are working hours and the wall-clock ratio bounds it in neither direction, so the query narrows to open, assigned, unbreached, unwarned and the calendar decides the rest. A window entirely inside non-working time returns early rather than dividing by zero. `SLA_80_PERCENT_ELAPSED` is an ESCALATION in the catalogue, so D-036 makes the mail unsuppressable — which follows from the category rather than being decided here, and is the right side to err on for an alert whose whole value is that it arrives. 9 tests; the weekend case is **mutation-checked** and its first draft was rewritten after the mutation passed — wall-clock and working hours both fell under the threshold, so it proved nothing.*
- [ ] **D-022** Stale-task nudge — no update for 3 working days, to assignee cc RM.
- [x] **D-023** 🔴 **Stage-SLA scanner, separate from ticket SLA** — a ticket can be well inside its PCD while rotting four days in the Deployment queue. Per-stage SLAs are what make the ribbon actionable rather than decorative. *(§16 item 3b)* — *`worker/sla/StageSlaScanner`. **A second scanner, not a branch in D-020**: the two answer different questions, alert different people (the *stage owner*, not the ticket assignee — the person who can unstick it is whoever it was handed to), and remember what they announced in different places. That last one is the interesting constraint: `ticket_stage_transitions` is append-only and A-008 permits exactly one mutation, sealing, so there is nowhere to put an "alerted" flag. The fact lives in its own `stage_sla_alerts` table keyed on the **transition**, not the ticket — a DEV → QA → DEV loop is three segments that can each breach separately — and `INSERT IGNORE` against the primary key makes the claim atomic without a lock. **The SQL prefilter is exact, not a guess**: working hours are never greater than wall-clock hours, so `TIMESTAMPDIFF(SECOND, entered_at, now) >= sla_hours * 3600` can only be too permissive, never too strict, and the calendar is consulted for the survivors. Computed per row against each stage's own budget — one `now - N hours` cutoff would apply one stage's SLA to all of them — and in seconds rather than `INTERVAL … HOUR`, which would truncate a 1.5-hour SLA to one. `sla_hours` is denominated in working hours, so the elapsed side is too (D-027); the test hands a ticket to QA on Friday evening with a 4-hour budget and asserts it has **not** breached by Monday morning, and **mutation-checking** confirms wall-clock maths fails it. 11 tests.*

- [x] **D-027** 🔴 **Every calculation routes through Stream B's working-hours service.** A Friday-18:00 ticket with a 4-hour SLA must not breach on Saturday morning. Do not write your own date maths. — *Realised in D-020 and enforced by a test rather than by a convention. The rule is narrower than it first reads: **durations** go through `WorkingHoursService`, **instants** do not. "Is this ticket past its Planned Close Date" is a timestamp comparison; "how far past" is a duration, and "overdue by 62 hours" counts a weekend nobody was working while "overdue by 6 working hours" is a number a manager can act on. `SlaScannerIT` pins it with a ticket that breached Friday 18:00 and is scanned Monday 10:00 — wall clock ~64h — asserting the reported figure is **both** under 24 and above zero. - [x] **D-032** 🔴 **Threading** — `Message-ID` and `In-Reply-To` headers keyed on the ticket, so a whole ticket's mail collapses into one Outlook/Gmail thread. — *`worker/outbox/MailThread`. **Every mail references a root that was never sent** (`<ticket.{id}@domain>`): synthesising it from the ticket id means the first mail and the fortieth point at the same ancestor with no query to find out which came first, and no orphaned thread when the first mail bounces. Clients thread on a referenced id whether or not they ever saw it. `In-Reply-To` **and** `References` are both set — Outlook leans on one, Gmail builds its conversation from the other, and setting one threads correctly in exactly one client. Message-IDs are keyed on the `email_log` row, not the ticket: a duplicate lets a client treat the second mail as a copy and drop it, which is indistinguishable from never sending it. **The trap is that JavaMail's `saveChanges()` overwrites `Message-ID` during send** — Spring's `JavaMailSenderImpl` reads the header first and puts an explicit one back, which is why it is set before the send and not in a preparator. That is invisible to a mock, so `MailThreadingIT` sends through a real `JavaMailSenderImpl` to a **Mailpit container** and reads back what was received; a unit test could only prove we asked. `message-id-domain` must be stable for the life of a deployment — changing it splits every existing thread in two. 13 unit tests, 5 in the IT.*
- [x] **D-033** Every send logged in `email_log` with status, provider message ID and retry count. Three retries, exponential backoff, then an in-app failure notification — **nobody should assume a mail arrived that never did**. — *Logging, retry count and backoff came with D-010; this adds the last clause. `worker/outbox/MailFailureNotifier` + `domain/notifications/NotificationWriter`. - [x] **D-034** Bounce and complaint webhooks — mark the address invalid, alert Admin. — *`POST /api/v1/webhooks/email/bounce` per contract (202/401). **New table `email_suppressions` — Stream A please review the shape**, there was nowhere to record address-level state.
